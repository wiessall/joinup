* How to read this
- *Triplestore = rdf_sync projection of SQL.* "Port X into the triplestore" means two
  things: an =rdf_sync= mapping in bundle or vocabulary config, and a declaration in this
  ontology of the predicate or class that mapping emits. Nothing here proposes storing
  anything in the graph that isn't in Drupal first.
- *Predicates are cheap to change; instance URIs are not.* A predicate change is a config
  edit plus a re-sync. An instance URI, once a partner or crawler has seen it, is
  permanent. So nearly all the foreclosure risk sits in P0.
- *Pattern first, then copy config.* Get one categorical+narrative pair (readiness) working
  end to end: vocabulary, term reference, projection, ontology term. After that, most of
  ATIO's ~80 fields are repetition of that pattern, not new design.
- Evidence comes from fork =edge= @ =fd52eab= (2026-09-16), v8 as uploaded, and your split.
  =build.py= output is quoted verbatim where cited.
- Folder status: =base_classes/= = MVP candidates (not all of it survives, see below);
  everything else = LATER or WONT. That matches your instinct, with two exceptions:
  =hasFieldClaim= lived in =probably_wont_implement/= but the fork emits it (now moved to
  =fieldClaim.ttl=), and =base_classes/= contains roughly as much to delete as to keep.

** TODO Stop minting FAO URIs in the EU Publications Office namespace
=node.type.collection= and =node.type.owner= still use Joinup's =joinup_po_namespace:w21=,
so every collection and owner is currently =http://data.europa.eu/w21/{uuid}=. Switch
both to =sti_namespace:<slug>=. Do this *before anything is published or shared*.
** TODO Instance URI pattern: https, and a fixed slug instead of the bundle id
=StiRdfUriGenerator= builds =http://sti-portal.fao.org/{bundle}/{uuid}=. Two problems:
- The bundle machine name is in the URI. Resolving question C by renaming =solution=
  would silently change every innovation URI. The plugin already prefers the derivative
  id (=$this->getDerivativeId() ?? $this->getEntity()->bundle()=), so
  =uri_plugin: 'sti_namespace:innovation'= pins the slug. That is config only.
- =http://= is hardcoded; switching to https is a one-line code change in the plugin. It
  needs a =hook_update_N= plus a full re-sync, which is cheap now and expensive later.
** DECIDE Namespaces: see OPEN ISSUE 12
Recommendation: two namespaces, split by ownership.
- =sti:= → =https://sti-portal.fao.org/ontology#=: platform (Unit 5). Innovation,
  FieldClaim, Annotation, inCollection, annotates, statedBy, claim*. Already emitted, so keep it.
- =sti_atio:= → =https://sti-portal.fao.org/ontology/sti-atio#=: ATIO's vocabulary
  (Valeria's). readinessLevel, adoptionLevel, thematicArea, narratives and so on. This
  *replaces* =collection/core#=, which is derived from field machine names and changes
  when a field is renamed.
- Retire v8's unused =sti: .../ontology/sti#= binding.
** TODO Make the namespace dereference
Serve =dist/sti-atio-base.ttl= at =https://sti-portal.fao.org/ontology/sti-atio= (FAIR, and
the "predictable stable URLs" constraint). Content negotiation can come later.

* Answers to the #? comments
The short versions are inline in the =.ttl= files as =#>= lines directly under each =#?=.
The ones that need more room are below.

** A1 fieldProvenance: "artifact of poor AI hygiene?"
Less bad hygiene than residue from the three-stage pipeline: it attributed fields on the
intermediate AIExtractedInnovation. The need behind it is real and protected by CON-03:
production's QA paragraphs carry a per-field "AI-generated" boolean. That is FieldQA's
job, and in the fork it's =core_annotation.quality_assessment=. WONT.

** A2 aiExtractedInnovation: "what's the upside?"
The upside it claimed was a buffer between raw and published, so you could re-run
enrichment without touching the published record, plus a place to merge sources before
curation. The fork already has that buffer, in Drupal: =solution= (raw) →
=core_annotation= in draft → published, and =rdf_sync_published= (enabled in
=core.extension.yml=) keeps drafts out of the graph. The one thing auditors legitimately
want from pipeline tracing is "which published values came from model X / prompt v3".
That is two or three properties on the annotation, not an entity. You lose multi-run
history in the graph; SQL revisions keep it.

** A3 innovationFamily: "will port but doesn't exist yet"
Fine as LATER. When you port it: make it a node bundle, not a taxonomy. The design
calls for temporal identity and split/merge history, which means revisions plus edges
between family entities, and terms have neither. Name the facets (=mechanism=, =domain=,
=target=, =context=, =form=) instead of =featureDimensionA..E=. Drop the
=correspondingConcept ≡ skos:exactMatch= equivalence (bug #1, shown by the build.py TRAP).

** A4 taxonomyMapping: "both collection → ATIO and collection ↔ collection"
As modelled it can't do the second one at all. It is per-record (=hasTaxonomyMapping= on
InnovationRecord), one-directional (=mappedToATIOConcept=), and it stores the source term
as a string (=sourceTaxonomyTerm=). That is also the wrong grain: "TechnoServe's 'Solar
water lifting' ≈ ATIO water-management" is a fact about the vocabulary, and v8 repeats it
on every innovation that uses the term. Your =claim_values= terms already have URIs, so:
: <claim_values/technoserve/solar-water-lifting> skos:closeMatch <atio/type/water-management> .
: <claim_values/technoserve/solar-water-lifting> skos:exactMatch <claim_values/gardian/solar-pumps> .
That's standard, VocBench-native and bidirectional by definition (=skos:closeMatch= is
symmetric). What you lose is per-mapping metadata (who validated it, and when). For the MVP
accept that; later, keep it on the Drupal field and don't project it.

** A5 dataSource: "merge with collection?"
Yes. =DataSource ⊑ dcat:Dataset= and the fork's =collection= is a =dcat:Catalog=, which is
itself a subclass of =dcat:Dataset= in DCAT 2/3, so nothing conflicts. It isn't urgent for
the triplestore beyond licence (P5). The rest is operational configuration, and Joinup's
=collection_settings= meta-entity is the right home for it: it's the same pattern you
already use for the facet source.

** A6 sourceRecord: "fits solution; solution can be edited, but it's versioned"
Revisions answer "what was the history of this node". v8's SourceRecord promises "what
did source X say, verbatim, at time T". Those come apart in three places:
1. rdf_sync projects the *current* revision only, so graph consumers never see history.
2. Claim history doesn't survive: =IrdClaims= hard-deletes superseded claim paragraphs,
   so earlier solution revisions point at paragraphs that no longer exist.
3. After a dedupe merge one solution carries claims from N collections but has one
   =field_machine_record=. Whose raw payload survives? =sti_dedupe= isn't on =edge=, so
   I couldn't check.
So solution works as SourceRecord only if you also decide its identity role. That's
OPEN ISSUE 13. The raw-preservation guarantee (ELT, auditability) is the part at risk,
and it fails silently.

** A7 fieldClaim: "claims are issued by collections, target any non-AI-curated class"
The fork gets the core right: =field_claimed_by= → =collection= (verified), and claims hang
on =solution=. v8 contradicts that in three places (see P2). One thing to be aware of:
"not innovations" holds only in your vocabulary. In the graph, =solution= *is*
=ontology#Innovation= and =core_annotation= is =ontology#Annotation=. So today, claims do
target the class called Innovation, and ATIO's curated record is the one that isn't.
That's question C showing up in the ontology. Whichever bundle takes the Innovation class,
the claim rule should read "claims target source-level entities, never
=sti:Annotation=", which is also a cleaner way to say it.

** A8 claimEligible: "not sure this belongs here"
It doesn't. Which properties go through claims is decided per collection by what's in
=claim_properties=. A second copy in the ontology is duplicate state, and it will drift.

** A9 ClaimResolution
It assumes a curator issues a verdict on each claim. At 200 × 1400 × 30 nobody will. In
your design the ATIO annotation *is* the resolution (AI synthesis, curator-reviewed), and
the claims are its evidence. Revisit only if a real per-claim review workflow appears.

** A10 claim eligibility and "lift the solution dedupe mechanism?"
Right: v8 puts claims *and* ATIO vocabularies on one entity, which is the "AI digest
inside the ATIO innovation" you're objecting to. In your design:
- claims carry *source* vocabulary values, on =solution=, scoped by collection;
- ATIO properties carry *ATIO* vocabulary values, on the annotation;
- the bridge between them is SKOS mapping (A4), and the AI enhancement uses it as input.
The not-eligible list in v8 (country, region, language) is exactly what the fork already
puts directly on =solution=, normalised. That's consistent.
On lifting dedupe: the compare-two-records UI and the "decision recorded" log carry over
well. The unit doesn't: dedupe decides entity identity, whereas claim comparison decides
a field value. Reuse the UI pattern for a curator "pick the value" step on the
annotation form. Don't reuse the merge service.

** A11 concept schemes: "I have the taxonomies already; do I need this?"
You need one =skos:ConceptScheme= per vocabulary, and rdf_sync can emit it from vocabulary
config, as the Joinup vocabularies do (=vid → skos:inScheme=). You don't need
hand-written representative concepts; their URIs won't match the ones your terms get.
Two caveats: in the fork the *claim* vocabularies exist but project nothing (P3), and the
*ATIO* vocabularies don't exist at all (=core_annotation= stores strings). Keep the CGIAR↔IDIA
=closeMatch= alignment only if both frameworks are really in use.

** A12 extra scheme marker classes: "belongs here? outdated?"
Outdated. Marker classes only earn their keep in a SHACL shape, and the only shape
targets readiness and adoption. For single-scheme properties, =skos:inScheme= already
says everything they do.

** A13 FieldSchemeUsage: "solved with claims scoped by collection"
Solved in Drupal: a value term's position under its collection in =claim_values= *is* its
scheme, so no declaration or inference rule is needed. Not yet solved in the graph,
because those vocabularies project nothing (P3). Fix that and the SPARQL
=?value skos:inScheme ?collectionScheme= works directly.

** A14 named graphs: "should I yield?"
Don't yield. Replace the design with the one you already have:
- =rdf_sync= writes to one graph (=rdf_sync.settings.graph_uri: http://data=).
- =rdf_sync_published= is enabled, so unpublished entities never reach the store.
- Access control is OG plus published state in SQL. "Internal" data (QA, workflow,
  curator notes) has no reason to be in the triplestore at all.
v8's three graphs are an access-control design for a system where the triplestore was
the store of record. Yours isn't. Named graphs start to pay off in one case: *published*
content that must still be partner-restricted over SPARQL. That would need either a
connector-level patch to route by bundle or a second endpoint. Park it as LATER, with
that trigger written down.

** A15 innovationRecord: "Joinup meta-entity pattern?"
Same conclusion as you, for a different reason. Joinup's =meta_entity= is a settings
sidecar attached to a group. InnovationRecord is the FRBR-style "information object about
the thing" (=foaf:primaryTopic=). It's semantically correct, but it doubles every URI and
turns every query into a hop through =isDescribedBy=. In the fork the node URI plays both
roles, and the management properties stay in SQL. The one idea worth keeping: the
real-world identity must survive record operations, which is the dedupe URI test in P0.

** A16 innovationSnapshot: "own class? RDF revisions? who'd query it?"
- RDF has no revisions. The options are one named graph per version (what
  =sparql_entity_storage= did), RDF 1.2 triple terms with a time annotation, or an n-ary
  node like InnovationSnapshot. The first two are poorly supported by rdf_sync and by
  most tools.
- It's *not* versioning. v8 itself separates it: it's time-qualified real-world state
  (TRL 5 in 2022, TRL 7 in 2024).
- Who'd query it: ATIO analysts doing readiness and adoption trajectories for the Outlook.
  That is Unit 1's sensemaking use case, so it's real.
- But a FieldClaim with =claimedAt= already *is* a time-stamped assertion. Keep superseded
  claims instead of hard-deleting them (P2 "Claim retention") and you have the trajectory,
  without a class. FieldTemporalValue gets the same answer.

** A17 bundleRelation: "don't see the point"
Production already rejected the separate entity: bundles are "typed relations between
innovation records". The n-ary class exists to hold confidence and curator confirmation
on the relation itself. That's workflow, so it belongs in Drupal: project only confirmed
relations, as binary predicates (=sti_atio:complementaryTo=, =requires=, =precedes=,
=coCitedWith=, all =⊑ schema:isRelatedTo=). LATER.

** A18 =dont_understand/atio_onth_type_definitions.ttl=
These are schema.org alignments, so a schema.org-aware consumer can read sti_atio data.
The idea is fine, but half the execution is a bug (bug #1). =owl:equivalentProperty= runs
in both directions: every =schema:name= anywhere implies =innovationName=, whose domain
then makes the subject an innovation. The pragmatic version is simpler still: wherever a
standard term exists, emit it directly from rdf_sync (the fork already does, with
dcterms:title and dcat:landingPage). Declare =rdfs:subPropertyOf= only for the few
custom =sti_atio:= terms. Also, =ownedBy ≡ dcterms:creator= is wrong on meaning: the
creator is =developedBy=.

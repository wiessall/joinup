#+TITLE: Agent API demo: raw data over REST, semantics over SPARQL
#+STARTUP: content

An agent, simulated by =curl= + =jq=, fetches a collection's solutions from
Drupal (REST, SQL of record) and their semantic connections from Virtuoso
(SPARQL, the rdf_sync projection plus SKOS mappings). The result is a map:
for each ATIO innovation field, which claims could fill it, directly or via
another collection's property, weighted by the SKOS relation.

| Diagram box                                              | Here                                   |
|----------------------------------------------------------+----------------------------------------|
| GET solutions of collection x without an ATIO innovation | step 1 (REST) + 1b (SPARQL)            |
| list of full solution content (json)                     | step 2, =/node/{nid}?_format=json=     |
| claims of the solution's collection ↔ ATIO fields        | step 3, =queries/01-claims-to-atio.rq= |
| duplicates of this solution                              | step 4, =queries/02-duplicates.rq=     |
| claim ↔ other_claim ↔ ATIO fields                        | step 5, =03-duplicate-claims-map.rq=   |
| the map (what generation consumes)                       | step 6, =04-field-candidates.rq=       |

* Weights
SKOS relation → weight, a convention kept as =VALUES= data in the queries:

| relation             | weight |
|----------------------+--------|
| skos:exactMatch      |    1.0 |
| skos:closeMatch      |    0.8 |
| skos:broadMatch      |    0.6 |
| skos:narrowMatch     |    0.6 |
| skos:relatedMatch    |    0.4 |

An indirect route (claim property ↔ other collection's property → ATIO
field) weighs the product of its two steps. Property-to-property mappings
are read in both directions. =sti:claimedAt= is import time, not which
source is semantically newer.

* Preparation (once)
** 1. Apply the patches and deploy
#+begin_src sh
git am 0009-*.patch 0010-*.patch 0011-*.patch
ddev exec 'vendor/bin/phpunit -c phpunit.xml web/modules/custom/sti_dedupe'
ddev exec 'vendor/bin/phpunit -c phpunit.xml web/modules/custom/sti_rdf'
ddev snapshot --name pre-demo
ddev drush deploy
#+end_src
=deploy= runs updb, cim (brings back =field_claim_ref_node=, adds
=skos:prefLabel= on claim terms), then the deploy hook
=restore_same_as_claims=, which writes the sameInnovationAs claims back onto
the solutions from =sti_dedupe_decision=. Check:
#+begin_src sh
ddev drush deploy:hook-status --format=json
ddev drush sqlq 'SELECT decision, COUNT(*) FROM sti_dedupe_decision GROUP BY decision'
ddev drush ws --type=sti_dedupe --count=10
#+end_src
A warning "The sameInnovationAs property term got the URI … instead of
https://sti-portal.fao.org/sti#sameInnovationAs" is harmless: the queries do
not depend on that URI.

** 2. Pick a solution with a duplicate in a second collection
If you have no "same" decisions between your two collections yet:
#+begin_src sh
ddev drush sti-dedupe:scan <collection>
#+end_src
then review at =/admin/content/dedupe= and press /Same innovation/ on one
or two pairs. The claims are written on both solutions at once.

** 3. Re-sync just the demo solutions
The graph still holds pre-P0 predicates for entities not saved since the
deploy. Re-save the demo solution(s); the script adds their duplicates,
their claims, the claim terms and the collections:
#+begin_src sh
ddev drush php:script TRISTAN_additions/demo/agent-api/prep-resync.php -- <nid> [<nid> …]
#+end_src
Stored URIs are unchanged, so rdf_sync replaces each entity's triples
cleanly. Check one solution:
#+begin_src sh
curl -s -H 'Accept: application/sparql-results+json' \
  --data-urlencode 'query=SELECT ?p ?o WHERE { <SOLUTION_URI> ?p ?o }' \
  http://digit-joinup-reference-2.ddev.site:8890/sparql | jq '.results.bindings[] | [.p.value, .o.value]'
#+end_src
Expect =https://sti-portal.fao.org/sti#hasFieldClaim= and =…sti#inCollection=.
=SOLUTION_URI= is the =uri= field in step 1's REST output.

** 4. Make the SKOS mappings
At =/admin/curate/skos= (log in first) pick sources per column, /Load/,
drag rows to align, set the relation, /Export Turtle/ → /Download/:
1. collection A → ATIO
2. collection B → ATIO
3. collection A → collection B

The export uses the URIs stored in the graph and adds =rdfs:label= for
every mapped term. Terms that were never synced are listed and left out.

Load all three into their own named graph. Not =http://data=: rdf_sync
rewrites a term's triples whenever the term is saved.
#+begin_src sh
G='https://sti-portal.fao.org/graph/mappings'
V='http://digit-joinup-reference-2.ddev.site:8890'
for f in skos_*.ttl; do
  curl -sS --digest -u dba:dba -X POST -H 'Content-Type: text/turtle' \
    --data-binary @"$f" "$V/sparql-graph-crud-auth?graph-uri=$G"
done
curl -s -H 'Accept: application/sparql-results+json' \
  --data-urlencode "query=SELECT (COUNT(*) AS ?n) FROM <$G> WHERE { ?s ?p ?o }" "$V/sparql" | jq '.results.bindings[0].n.value'
#+end_src
To start over: =curl --digest -u dba:dba -X DELETE "$V/sparql-graph-crud-auth?graph-uri=$G"=.

Optional, for duplicate review rather than the demo: also put each
=exactMatch= to ATIO into the property term's =field_atio_property=;
that is what =sti_dedupe= uses to detect conflicting claims.

* Running the demo
#+begin_src sh
cd TRISTAN_additions/demo/agent-api
COLLECTION=<nid|uuid|alias> SOLUTION_NID=<nid> ./agent.sh
#+end_src
Each step prints a line and writes its JSON to =out/=:

| file                             | what                                                     |
|----------------------------------+----------------------------------------------------------|
| =01-solutions.json=              | REST list of the collection's solutions, with graph =uri= |
| =02-without-innovation.json=     | those with no ATIO innovation derived from them          |
| =03-solution.json=               | full Drupal JSON of the chosen solution                  |
| =04-claims-to-atio.json=         | its claims, each with direct/indirect ATIO routes        |
| =05-duplicates.json=             | solutions marked as the same innovation                  |
| =06-duplicate-claims-map.json=   | their claims ↔ main claims ↔ ATIO fields                 |
| =07-field-candidates.json=       | the map, as SPARQL results                               |
| =08-field-map.json=              | the map, compacted per ATIO field                        |

Then open =map.html= in a browser and drop =out/07-field-candidates.json=
on it: one lane per ATIO field, candidate claims ranked by weight, solid
for direct, dashed through the other collection's property for indirect,
blue for the solution's own claims, orange for its duplicates'.
See =example-map.png=, rendered from the test fixture.

Without =SOLUTION_NID= the agent takes the first solution that has no
innovation, which is unlikely to have a duplicate: pass it for the demo.

* Limits to say out loud
- No REST filter for "without an innovation": none exist yet, so step 1b
  answers it from the graph instead.
- =/api/collection-solutions/v1= returns at most 200 solutions.
- In =/node/{nid}?_format=json= the claims are paragraph references; their
  content comes from SPARQL.
- Weights are a convention, not something the curator states per mapping.
- The graph is consistent only for re-synced entities until the full
  re-mint and rebuild (=drush sti-rdf:uri-remint=, drop graph, resync).

#+Title: README

This README describes the exploration of joinup and outlines a possible migration from the existing portal into a joinup-based distribution.

Areas of exploration are
1. RDF data modelling: How to design the knowledge graph, considering Valeria's needs
2. Drupal data modelling: Creation of simpler core bundles; plan migration from old portal
3. MVP: The ongoing development of a joinup-based system that solves our current use cases
4. UI/UX: Joinup's paragraph system; groups; social features

*Structure*
#+begin_src
python - addtions to the IRD python library; introduces support for standard json schema
rdf - ttl and trig files designing the triplestore. Contains my assesments and Valeria's ideal and a python visualization tool
drupal - the drupal-side data modelling: graphs and tables outlining current structure and possible migrations
archive - things to delete
#+end_src

** First Principles of STI Portal re-design
  1. Deliver what was promised: The sources of truth for design are the Capex proposal and the ATIO design doc. We need to first and foremost make sure that we deliver what's outlined there.
  2. Engine & content moderation remain in Drupal
     + Team is skilled for that; we have good pool of consultants; de-facto standard in public sector
  3. True support of data federation and knowledge graphs
     + use joinUp
  4. Ensure the ability to collect data on Agricultural innovation from within and outside of FAO.
     + This requires the semantic web principle "Anyone can say Anything about Anything (AAA)"
  5. Modular design: Provide a stable core of data storage and management (see point 1). Connect chatbots etc through API. Separate AI-generated content into different areas of the data model & track the AI origin.
*** Philosophy
  - There is no such thing as 'innovation'. Taking ATIO's definition is presumptous. Rather: Anybody can say Anything about Anything: Let people keep their language and derive a consensus. It's not important what an 'Innovation' is it's important how people talk about it. Defining 'innovation could be outcome of 5. far future.
*** Risks
   - SKOS-mapping and pruning carries a lot of weight
   - Can this be reflected in joinup?
   - Is this store a rdf pattern that federates well?
   - What if a source makees statements not only about innovations but also organizations?
     + Write two different migrations? Split this in the json generation (but python script simple & dumb)?
   - What about new content types? The design doc forsees 'Initiative', 'Innovation Family' etc
     + I could keep slim core 'solution' from joinup and make innovation, initiative etc children
     + But how to separate them semantically? I know AAA but at some point we will have to set boundaries as to which fields/statements are tied to which core classes, no?

** UI: Filter by claim
The basic idea of the re-design is that we keep the original dimensions (e.g. columns in an excel file) of assessment of an innovation of each collection. This ensures that we don't have to discard anything and it maps well to the AAA principle of the semantic web.

So far we manage to create drupal paragraphs (referred to in a ~solution~ ~field_claim~ field) that contain: ~claimed_by~ ~claim_property~ and ~claim_value~. Drupal-side we automatically populate two taxonomy vocabularies: One for the collections 'properties' (the rdf term for 'keys') and one for it's 'values' (only if they are deemed categorical; otherwise values are stored as strings).

If we manage to also index the claim paragraph fields, we can offer faceted search that uses this search-index representation in a search-index view. An alternative would be a traditional view that displays multi-select filters automatically, if the referenced data is in a taxonomy.

2026-06-09: Implemented an automatic view builder. The resulting default/page/block view exposes all categorical (i.e. stored in taxonomy vocab) facets & tiles of the resulting solutions. Downside: 1 new view/block per collection. Alternative: 1 block that contains /all/ facets from /all/ collections & a hook that shows/hides them based on path.
** Joinup & Open social integration
This is a general question: Should this be done? Joinup uses an older model of groups, but allows for messaging, posting news/events etc already. Factoring this out & interfacing with open social's newer group model could introduce unneccesary complexity.

High-level concept: Joinup keeps track of editing rights. Anyone in joinup ~col_A~ with role 'facilitator' gets mapped to 'group manager' in open social. Open social gets an api view into the corresponding collection's solutions.

How would editing on open social happen? How much automisation is possible in creating open social groups based on joinup og-audiences?

#+Title: README - MVP

* Scope
The MVP shows the proof that a joinup-based STI portal will be able to achieve the project aims as defined in the CAPEX proposal and the ATIO design doc.
It will deliver:
** Sitemap
  - Welcome: Landing page with access to ATIO and STI collections
  - Collection pages
    + Faceted search
    + Customization of about, logo, banner
    + ~source_record~ (> 100) and ~atio_innovation~ (2-3)
** Datamodel
  - ~source_record~: fully modeled in both RDF and SQL
  - ~atio_innovation~: fully modeled in both RDF and SQL
  - ~collection~: fully modeled in both RDF and SQL
  - ~claim~: fully modeled in both RDF and SQL
** Curation views
  Curators will be able to solve
  - deduplication of ~source_record~
  - update of a semantic map using skos and projected to the triplestore
  - editing of all 4 types of the current data model in dedicated views
  - QA review of relevant content
** Data access
  - ~source_record~ will be readable using REST
  - all data will be accessible using SPARQL
  - ~atio_innovation~ will be writeable using REST
** Out-of-scope
  - ECAs / algorithms transforming ~source_record~ into ~atio_innovation~
  - Full UX/style copy of current site (e.g. ATIO landing page)
  - Innovation family has to be actually figured out by ATIO
  - Integration with open social will be built later
  - Joinup pruning / new distribution generation will happen later

** REST API and GET access                                          :datalab:

Joinup uses the ~rest~ module (config: /admin/config/services/rest) to define REST endpoints one-by-one. I prefer this over the REST-JSON module, because that one opens REST endpoints to any node in the system. The preferred control to only open access to specific resources makes more sense from a security perspective.
*** GET: Collection-scoped content
The relevant GET endpoint is: ~/api/collection-solutions/v1/{collection}: GET~. It is defined by the ~sti_portal_api~ module. It retrieves all content for a given collection. Filters are:
 + ~?moderation=|all|published|unpublished|~ : published status. Default: published
 + ~?type=|source_record|atio_innovation|~ : which content types, comma-separated
 + ~?include=claims~ : whether or not to include the claim information. Default: false
 + ~?limit=N~ : set a maximum amount to content to retrieve. This copies the pagination on the collection, so a page needs to be speciefied. Default: no limit
 + ~?page=P~ : page through results. Default: all pages
** Drupal: ~source_record~ -> ~atio_innovation~ derivation and AI-enrichment
Improving the traceability, quality and modularity of the creation of the ~atio_innovation~ is the core reason for the creation of this MVP. While the STI namespace now handles data input of any strucuture, it results in collections that each present data in their own, unique way. The important step is standardization: The derivation of comparable innovation records requires a centralized format. This is provided by the ATIO team; the only thing changing is the input format of the data they work with to derive this standardized view.

** ~sti_dedupe~
Deduplication is an important task an registered as not fully resolved in the current ATIO design document. It could be done at the ~source_record~ or the ~atio_innovation~ level. This module solves it at the ~source_record~ level. The rationale is that data input from many different sources might likely contain duplicates. Registering this early will allow to map potentially differing claims from different collections about the same ~source_record~ possible. It also makes the derivation of an ~atio_innovation~ easier. Technically this is solved by another field on the claims paragraph: ~duplicate_of~ has claimedAt and claimedBy fields. This also solves the issue of agreement: If collection A claims ~source_record~ A is a duplicate of ~source_record~ B from collection B this statement is recorded. Only if collection B also makes the reverse claim do we have a confirmed agreement.
The module provides an easy interface for data curators to register this duplicate claim.

** ~sti_portal_api~
  This module provides the API endpoint to read a collection's content. It should be the main entrypoint to the system that is being built by the datalab colleagues to get content data. Ideally it is used in conjunction with sparql queries that provide semantic context to the content.
  For the data retrieval it is assumed that it is done per-collection and that the user only wishes to filter by publication status, content type and whether or not to add the detailed claims or to only return the content core fields.
 + ~?moderation=|all|published|unpublished|~ : published status. Default: published
 + ~?type=|source_record|atio_innovation|~ : which content types, comma-separated
 + ~?include=claims~ : whether or not to include the claim information. Default: false
 + ~?limit=N~ : set a maximum amount to content to retrieve. This copies the pagination on the collection, so a page needs to be speciefied. Default: no limit
 + ~?page=P~ : page through results. Default: all pages
